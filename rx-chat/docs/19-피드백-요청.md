## 1. 무엇을 만드는가

굿팜 **고객앱**의 **처방 Context 기반 Guided AI Chat**이다.

고객이 처방전을 등록하면 이전 처방과 비교해 이번에 무엇이 달라졌는지 설명하고,
공식 근거(의약품 정보 · DUR)를 출처와 함께 보여주며, 필요하면 약사 연결이나 내 주변 약국 재고 찾기로 이어준다.
진단 · 처방 변경 권고 · 복용 여부의 최종 판단은 하지 않는다. 그 판단은 약사가 한다.

```text
처방전 촬영(지킴 OCR) → 단말에 처방 데이터 저장 → 새 처방 등록
 ├ 이전 처방 있음 → 비교(Rule Engine) → 처방 카드로 변화 설명
 └ 이전 처방 없음 → 이번 처방 정리 (다음 처방부터 비교)
→ 더 궁금한 점 선택 → 근거 기반 답변 → 약사 연결 / 약국 재고 찾기
```

이전 처방이 없는 고객도 이번 처방 카드에서 후속 질문과 약국 연결까지 이어진다.

| 구분 | 내용 |
|---|---|
| 최종 사용자 | 고객. 약사 쪽은 AI MATE `고객 종합 분석` 탭의 내부 검증 영역 |
| 데이터 원천 | 처방전 등록(핵심) · 영수증과 일반약(보조) |
| 처방 이력 저장 | 고객 단말 (MVP Privacy-by-Design) |
| 판정 | Rule Engine. LLM은 설명 문장만 |
| MVP 답변 | 정해진 문장 틀에 판정 값을 채우는 템플릿 + 출처 |
| 다음 단계 | LLM 구조화 출력 → RAG |

## 2. 확정된 기준 (검토 대상)

### 2.1 처방 변화 판정

| 항목 | 기준 |
|---|---|
| 이번 처방 | 가장 최근 처방일 묶음 |
| 비교 범위 | 최근 6개월 |
| 동일 약물 | **성분코드 앞 4자리** (제형 뒤 2자리 제외). 굿팜 AI mate가 쓰는 기준과 같다 |
| ATC 코드 | 치료군 비교 보조 |
| 상태 | NEW · CHANGED · CONTINUE · 미포함(남음) · 미포함(종료) + 장기복용 표시 |
| CHANGED 판단 값 | 제품 · 함량 · 1회 투여량 · 1일 횟수 (숫자와 단위를 나눠 비교) |
| 최근 처방 미포함 | 투약일수가 남았는지 끝났는지로 나눈다. 복용 중단으로 단정하지 않는다 |
| 장기복용 | 굿팜 AI 약력관리에 이미 구축된 기준을 그대로 쓴다 (기준값 확인 중) |
| 우선순위 | NEW → CHANGED → 미포함(남음) → 장기복용 → CONTINUE |
| 고객 카드 대상 | 위 다섯 가지. 미포함(종료)은 `빠진 약이 있나요?` 답에서 알려준다 |
| 카드 수 | 최대 3개 |

### 2.2 처방 카드 구성

상태·약물명 / 요약 한 줄 / **이전·이번 비교표**(제품 · 1회 투여량 · 복용 횟수 · 투약일수 · 함량) /
알아두면 좋은 내용 / 더 궁금한 점(상태별 칩 3개) / 약국 연결(전화·채팅) / 근거 보기(사용 근거 · 비교 처방일)

약국에 물어볼 문장은 답이 `현재 제공된 정보만으로는 판단하기 어렵습니다.`로 끝날 때만 그 아래에 한 줄로 붙는다.

### 2.3 대화 방식

말풍선을 고르면 답이 나오고 후속 질문 2~3개가 붙는 **선택형 Guided Chat**이다. 직접 입력은 보조다.
챗봇 첫 화면은 단말에 쌓인 처방 묶음 수로 세 갈래로 나뉜다. 비교 질문(`달라진 점` · `새로 추가된 약`)은 비교할 이전 처방이 있을 때만 보여준다.

### 2.4 데이터 처리

| 층 | 무엇 | 처리 |
|---|---|---|
| Personal | 처방 데이터 · 판정 결과 | 고객 단말 저장. AI에는 최소 변화 정보만 보내고 서버에 누적하지 않는다 |
| Public | 의약품 정보 · DUR · 굿팜 안내 | MVP는 정해진 필드 조회, 이후 RAG 색인 |
| Dynamic | 약국 실재고 | 요청할 때 최신값 조회 |

AI에 보내는 최소 Context 예시

```json
{ "drug": "인데놀정10mg", "changeType": "CHANGED",
  "changedField": "1회 투여량", "before": "1정", "after": "2정" }
```

### 2.5 약 찾기 · 재고

약품 상세의 Action(`내 주변 약국 재고 찾기`) → 지도 · 목록 → 약국 Bottom Card.
약국 상세에서 약품을 검색하는 경로도 있고, 두 경로가 같은 재고 데이터를 쓴다.
대상은 **약학정보원에 등록된 약(일반·전문)** 이고, 전문의약품에는 `처방전이 있어야 조제되는 약입니다`를 함께 둔다.
재고는 수량 · 기준 시각(최종 반영 시각) · 실제와 다를 수 있다는 안내 · 약국 연락처를 함께 보여주고,
없을 때는 `현재 확인된 재고 없음`으로 쓴다.

### 2.6 검증 계획

| 단계 | 내용 |
|---|---|
| 1차 내부 검증 | 한일약국(테스트 약국) 조제 이력 · 6주 · 사내 약사 + 한일약국 약사 교차 검토 |
| 2차 고객 파일럿 | 사내 체험 2주 → 참여 약국 2곳 고객 대상 8주 |
| 목표 | 판정 정확도 98% · 불필요 알림 20% 이하 · 약국 문의 전환율 15% · 재이용률 30% |
| AI 비용 | LLM 답변을 도입하는 단계 기준 카드 1건 약 14원 (Sonnet 5, 입력 2,450 · 출력 550 토큰 가정). MVP 템플릿 답변 구간은 판정 값을 문장 틀에 채워 만든다 |

## 3. 검토해 주셨으면 하는 것

### 3.1 제품 방향

| 번호 | 쟁점 | 지금 선택 | 봐 주셨으면 하는 점 |
|---|---|---|---|
| 1 | 최종 사용자 | 고객 | 고객이 처방전을 **반복해서** 올릴 이유가 충분한지. 첫 등록 뒤 두 번째 처방이 쌓여야 핵심 가치가 나오는 구조의 위험 |
| 2 | 처방 이력을 단말에만 저장 | MVP Privacy-by-Design | 기기 변경 시 이력이 끊기는 불편을 고객이 받아들일지. 서버 저장으로 바꿀 판단 시점의 기준 |
| 3 | 선택형 Guided Chat | Chip 선택, 직접 입력은 보조 | 선택만으로 고객의 질문을 충분히 담는지. 직접 입력을 열어야 하는 지점 |
| 4 | MVP 답변을 템플릿으로 | 문장 틀 + 판정 값 | 템플릿 답변으로 고객이 가치를 느낄 수 있는지, 아니면 첫 버전부터 LLM 구조화 출력이 필요한지 |
| 5 | 재고 수량 공개 | 수량 + 기준 시각 + 차이 안내 | 실제와 다를 때 생길 고객 불만과 약국 부담. 수량 대신 보유 여부만 두는 편이 나은지 |

### 3.2 판정 규칙

| 번호 | 쟁점 | 봐 주셨으면 하는 점 |
|---|---|---|
| 6 | 동일 약물 = 성분코드 앞 4자리 | 제형이 다른 약을 같은 약으로 묶는 데서 생길 오판(예: 정제와 시럽, 서방정과 속방정) |
| 7 | 비교 범위 6개월 | 만성질환 장기 처방에서 6개월이 적절한지 |
| 8 | 카드 최대 3개 · 우선순위 | 우선순위가 고객이 중요하다고 느끼는 순서와 맞는지 |
| 9 | `최근 처방 미포함` 표현 | 고객이 "약이 빠졌다"를 불안 없이 받아들일 표현인지 |
| 10 | 장기복용 기준 | 기준값과 별개로, 약사용 약력관리에서 쓰던 기준을 고객이 보는 화면에 그대로 가져오는 방식이 맞는지 |

### 3.3 안전 · 표현

| 번호 | 쟁점 | 봐 주셨으면 하는 점 |
|---|---|---|
| 11 | 답변 구조 | `확인된 사실 + 판단 한계 + 필요 시 약사 연결`이 의료 표현 범위 안에 있는지 |
| 12 | DUR을 근거로 쓰는 것 | 병용주의 · 중복은 처방 데이터로 판정하고, 임부금기 · 연령주의는 고객이 물었을 때 답한다. 이 수위가 맞는지 |
| 13 | 증상과 연결되는 질문 | `최근 불편한 증상과 관련이 있을 수 있나요?` 같은 질문이 진단으로 읽히지 않는지 |
| 14 | 전문의약품 재고 노출 | 광고·유인으로 읽힐 소지와 완화 방법 (법무 확인과 별개로 제품 관점에서) |
